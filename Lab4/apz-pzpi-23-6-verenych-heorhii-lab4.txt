1 ЗАВДАННЯ

Мета роботи: дослідити та реалізувати спосіб масштабування backend-частини системи управління спортивними командами SportManager для роботи з більшим навантаженням.

У межах лабораторної роботи необхідно:
Обрати стратегію масштабування backend-частини системи.
Описати технічні рішення, які дають змогу масштабувати систему.
Реалізувати запуск кількох копій backend-сервера.
Налаштувати балансування запитів між backend-інстансами.
Перевірити, що запити розподіляються між кількома копіями backend.
Проаналізувати можливі вузькі місця системи при збільшенні навантаження.
Описати перевірку роботи системи після масштабування.

2 ХІД ВИКОНАННЯ РОБОТИ

2.1 Загальний опис масштабування backend
Програмна система SportManager складається з кількох основних частин: web-застосунку (React + Vite), мобільного застосунку (Android/Kotlin), backend-сервера (Node.js/Express) та бази даних PostgreSQL.
У звичайному режимі роботи всі клієнтські частини системи звертаються до одного backend-сервера. Backend приймає HTTP-запити, обробляє їх, звертається до бази даних PostgreSQL та повертає результат користувачу.
Початкова схема роботи системи мала такий вигляд:
Web / Mobile / Postman – Backend – PostgreSQL

Для лабораторної роботи було реалізовано масштабування backend-частини. Основна ідея полягає в тому, що замість одного backend-сервера запускається кілька однакових копій. Перед ними розміщується Nginx Load Balancer, який приймає запити від користувачів і розподіляє їх між доступними backend-контейнерами.
Після масштабування схема роботи системи має такий вигляд:
Web / Mobile / Postman – Nginx Load Balancer – backend-1, backend-2, backend-3 – PostgreSQL

Така схема відповідає горизонтальному масштабуванню, оскільки кількість backend-серверів збільшується за рахунок запуску додаткових копій одного й того самого сервісу.

2.2 Обрана стратегія масштабування
Для системи SportManager було обрано горизонтальне масштабування backend-сервера.
Горизонтальне масштабування означає, що система запускає кілька однакових копій backend-сервера. Кожна копія виконує однакові функції: обробляє запити авторизації, роботи з командами, гравцями, тренерами, подіями, відвідуваністю, медичними картками, статистикою та інвентарем.
У межах лабораторної роботи backend було запущено у трьох копіях: backend-1, backend-2, backend-3.
Усі три backend-контейнери працюють з однією спільною базою даних PostgreSQL. Це можливо, тому що backend не зберігає критичний стан у пам'яті конкретного контейнера. Основні дані системи зберігаються в базі даних.
Користувач при цьому не звертається до конкретного backend-контейнера. Для нього існує одна адреса:
http://localhost:80
На цій адресі працює Nginx, який розподіляє запити між backend-контейнерами.

2.3 Використання Nginx як Load Balancer
Для балансування запитів між backend-контейнерами було використано Nginx. Він виконує роль проміжного сервера між клієнтом і backend-інстансами.
Клієнтська частина системи надсилає запити на адресу локального сервера, цей запит спочатку потрапляє до Nginx. Далі Nginx передає його одному з доступних backend-контейнерів.
Фрагмент конфігурації:

events {
  worker_connections 1024;
}

http {
  upstream sportmanager_backend {
    server backend:3000;
  }

  server {
    listen 80;

    location / {
      proxy_pass http://sportmanager_backend;
      proxy_http_version 1.1;
      proxy_set_header Host $host;
      proxy_set_header X-Real-IP $remote_addr;
      proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
      proxy_set_header X-Forwarded-Proto $scheme;
      proxy_set_header Connection "";
    }
  }
}

У цьому фрагменті upstream sportmanager_backend визначає групу backend-серверів, на які Nginx може передавати запити. Оскільки backend запускається через Docker Compose у кількох копіях, Nginx може спрямовувати запити на різні інстанси одного сервісу.

2.4 Масштабування backend через Docker Compose
Для запуску системи використовується Docker Compose. У ньому описано сервіси PostgreSQL, backend та Nginx.
Фрагмент конфігурації backend у docker-compose.yml:

backend:
  build:
    context: .
    dockerfile: Dockerfile
  restart: always
  environment:
    DB_HOST: postgres
    DB_PORT: 5432
    DB_NAME: sports_team_db
    DB_USER: postgres
    DB_PASSWORD: 6CXL58cZ
    JWT_SECRET: sports_team_jwt_secret_2025_xk9mq7z
  expose:
    - "3000"
  depends_on:
    postgres:
      condition: service_healthy
  networks:
    - sportmanager_network

У backend-сервісі не використовується container_name, оскільки це завадило б створенню кількох контейнерів одного сервісу. Docker Compose автоматично створює контейнери з назвами backend-1, backend-2, backend-3.
Для запуску одного backend-сервера використовується команда:
docker compose up --build --scale backend=1
Для запуску трьох backend-серверів використовується команда:
docker compose up --build --scale backend=3

2.5 Endpoint для перевірки backend-інстанса
Для наочної перевірки горизонтального масштабування було створено службовий endpoint:
GET /system/instance
Він повертає інформацію про backend-контейнер, який обробив конкретний запит.
Фрагмент коду маршруту (routes/system.js):

const express = require('express');
const router  = express.Router();
const os      = require('os');

router.get('/instance', (req, res) =&gt; {
  res.json({
    status: 'OK',
    service: 'SportManager Backend',
    currentBackendInstance: os.hostname(),
    pid: process.pid,
    time: new Date().toISOString(),
  });
});

module.exports = router;

Кожен Docker-контейнер має власний hostname. Тому під час багаторазового звернення до endpoint можна побачити, який саме backend-контейнер обробив кожен запит.

2.7 Вертикальне масштабування backend
Окрім горизонтального масштабування, для системи можливе також вертикальне масштабування. Воно полягає не в збільшенні кількості backend-контейнерів, а в збільшенні ресурсів одного backend-інстанса.
Наприклад, одному backend-контейнеру можна виділити більше процесорного часу та оперативної пам'яті. Це дозволяє одному серверу обробляти більше запитів без запуску додаткових копій.
Приклад налаштування ресурсів у Docker Compose:

deploy:
  resources:
    limits:
      cpus: "2.0"
      memory: 512M
    reservations:
      cpus: "1.0"
      memory: 256M

Таке рішення може бути корисним, якщо система працює на сервері з достатнім запасом ресурсів. Однак вертикальне масштабування має природні обмеження, тому що ресурси одного фізичного або віртуального сервера не можна збільшувати нескінченно.
У межах лабораторної роботи основний акцент зроблено саме на горизонтальному масштабуванні, оскільки воно краще демонструється через кілька backend-контейнерів і load balancer.


3 АНАЛІЗ ВУЗЬКИХ МІСЦЬ

Після масштабування backend-сервера навантаження на обробку HTTP-запитів розподіляється між кількома контейнерами. Це зменшує навантаження на один backend-інстанс і підвищує стійкість системи.
Однак у системі залишаються ресурси, які можуть стати вузькими місцями при великому навантаженні.
Першим вузьким місцем є база даних PostgreSQL. Усі backend-контейнери звертаються до однієї спільної бази даних. Якщо кількість запитів значно зросте, саме база даних може першою почати працювати повільніше, оскільки їй потрібно обробляти запити від усіх backend-інстансів.
Другим вузьким місцем є пул підключень до бази даних. Бібліотека node-postgres використовує пул підключень для роботи з PostgreSQL. Якщо кількість одночасних запитів стане більшою, ніж кількість доступних підключень у пулі, частина запитів буде чекати на вільне підключення.
Третім вузьким місцем можуть бути ресурси комп'ютера, на якому запускаються Docker-контейнери. Оскільки в лабораторній роботі система запускається локально, усі контейнери використовують ресурси одного комп'ютера: CPU, RAM і дискову підсистему.
Четвертим можливим обмеженням є Nginx, але в межах лабораторної роботи він не є критичним вузьким місцем, оскільки для локальної демонстрації його продуктивності достатньо.


4 ПЕРЕВІРКА РОБОТИ СИСТЕМИ ПІСЛЯ МАСШТАБУВАННЯ

Після запуску трьох backend-контейнерів було перевірено роботу основного API та web-частини системи.
Спочатку було перевірено службовий endpoint:
http://localhost:80/system/instance
Він показав, що запити обробляються різними backend-контейнерами. Після цього було відкрито web-інтерфейс системи SportManager. Система продовжила працювати так само, як і при одному backend-сервері. Адміністратор може увійти до системи, переглянути список команд та гравців, додати нову подію та переглянути статистику.

Таким чином, масштабування backend не порушило взаємодію з базою даних та клієнтськими застосунками.

5 ОПИС НАВАНТАЖУВАЛЬНОЇ ПЕРЕВІРКИ

У межах лабораторної роботи не проводилося повноцінне навантажувальне тестування за допомогою JMeter або Gatling, оскільки основна мета роботи полягала в демонстрації можливості масштабування backend-сервера.
Для базової перевірки було використано серію повторних API-запитів до endpoint /system/instance. Цей endpoint дозволив перевірити, що запити розподіляються між різними backend-інстансами. Порівняння режимів запуску наведено в таблиці 1.

Повноцінне навантажувальне тестування може бути виконане в подальшому з використанням JMeter, Gatling або Locust. У такому тестуванні можна виміряти кількість запитів на секунду, середній час відповіді та відсоток помилок для конфігурацій з одним, двома та трьома backend-інстансами
6 ВИСНОВОК

У ході виконання лабораторної роботи було реалізовано масштабування backend-частини системи управління спортивними командами SportManager.
Для масштабування було використано горизонтальний підхід. Backend-сервер було запущено у трьох однакових Docker-контейнерах: backend-1, backend-2 та backend-3. Перед ними було розміщено Nginx Load Balancer, який приймає запити на порту 80 і розподіляє їх між доступними backend-інстансами.
Для перевірки було створено службовий endpoint GET /system/instance, який повертає ідентифікатор backend-контейнера, що обробив запит. Під час багаторазового звернення до цього endpoint було підтверджено, що горизонтальне масштабування працює коректно: запити розподіляються між різними backend-контейнерами.
Також було розглянуто можливість вертикального масштабування backend-сервера шляхом збільшення ресурсів одного контейнера. Однак основний акцент у роботі зроблено саме на горизонтальному масштабуванні, оскільки воно краще підходить для web-систем і дозволяє збільшувати кількість backend-копій залежно від навантаження.
У результаті було показано, що система може працювати не лише з одним backend-сервером, а й з кількома копіями backend, при цьому web-застосунок та база даних PostgreSQL продовжують працювати коректно.
