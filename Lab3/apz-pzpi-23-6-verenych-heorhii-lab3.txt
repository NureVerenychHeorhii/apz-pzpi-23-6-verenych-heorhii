1 ЗАВДАННЯ

Мета роботи: розробити та описати front-end частину системи управління спортивними командами SportManager, зосередивши увагу на web-застосунку для адміністратора та тренера, а також окремому особистому кабінеті гравця, його взаємодії з backend-сервером та базою даних PostgreSQL.

У межах лабораторної роботи необхідно:
– описати призначення та функціональність web-застосунку системи;
– реалізувати окремий web-інтерфейс для адміністратора та тренера;
– реалізувати особистий кабінет гравця з доступом до персональних даних;
– описати прийняті інженерні рішення під час розробки web-частини;
– описати взаємодію компонентів web-застосунку між собою та з backend;
– розробити UML-діаграму прецедентів для web-частини системи;
– розробити UML-діаграму компонентів;
– побудувати діаграму пакетів та діаграму взаємодії;
– описати реалізовані функції: авторизацію, управління командами, гравцями, подіями, відвідуваністю, статистикою, медпунктом та інвентарем;
– перевірити роботу web-застосунку та сформулювати висновки.

2 ХІД ВИКОНАННЯ РОБОТИ

2.1 Загальний опис web-застосунку

Система SportManager призначена для автоматизації основних процесів спортивного клубу. У межах цієї лабораторної роботи основний акцент зроблено на розробці web-частини системи, яка забезпечує роботу адміністратора, тренера та гравців.

Web-застосунок виконує роль основного робочого інтерфейсу для персоналу клубу. Через нього адміністратор та тренер можуть керувати командами, гравцями, подіями, відвідуваністю, статистикою, медпунктом та інвентарем. Гравець через особистий кабінет переглядає власні дані, розклад подій, статистику та медичну картку.

Архітектура web-частини побудована за клієнт-серверним принципом. Web-застосунок не звертається до бази даних безпосередньо. Усі операції виконуються через REST API backend-сервера, який обробляє запити та звертається до PostgreSQL.

Загальна схема взаємодії:
– React web-застосунок → REST API backend → PostgreSQL database

Для реалізації web-частини використано React 19 з Vite 8 як збирачем. HTTP-запити до backend виконуються через власний fetch-клієнт (utils/api.js) з автоматичним підстановленням JWT-токена з localStorage. Маршрутизація між сторінками реалізована через React Router DOM 7. Стилі визначено у єдиному файлі App.css без зовнішніх CSS-фреймворків.

2.2 Опис ролей користувачів web-застосунку

У web-частині системи реалізовано три ролі користувачів:
– адміністратор (admin);
– тренер (coach);
– гравець (player).

Адміністратор та тренер використовують спільний інтерфейс зі спільним набором навігаційних розділів. Відмінність полягає в тому, що адміністратор додатково має доступ до розділу «Права доступу» для управління ролями користувачів. Тренер не має можливості змінювати ролі облікових записів.

Гравець має окремий кабінет з особистими даними. Він не бачить агрегованої інформації по клубу, а лише власні події, статистику, медичну картку, склад своєї команди та профіль.

2.5 Реалізація взаємодії web-застосунку з backend

Для взаємодії web-застосунку з backend створено єдиний API-клієнт у файлі utils/api.js. У ньому реалізовано функцію request(), яка автоматично підставляє JWT-токен з localStorage у заголовок Authorization кожного запиту. При отриманні статусу 401 токен та дані користувача видаляються, а користувача перенаправляється на сторінку авторизації.

API-клієнт надає чотири методи: api.get(url), api.post(url, data), api.put(url, data), api.delete(url). Базовою адресою є /api, що через Vite proxy перенаправляється на http://localhost:3000.

У web-застосунку реалізовано запити до backend для таких операцій:
– POST /auth/login — авторизація користувача;
– GET /dashboard — агреговані KPI-показники клубу;
– GET, POST, PUT, DELETE /teams — CRUD команд;
– GET, POST, PUT, DELETE /players — CRUD гравців;
– GET, POST, PUT, DELETE /events — CRUD подій;
– GET, POST, PUT /attendance — відмітки відвідуваності;
– GET, POST, PUT, DELETE /stats — статистика гравців;
– GET, POST, PUT, DELETE /injuries — медичні записи;
– GET, POST, PUT, DELETE /inventory — інвентар;
– GET, PUT /admin/users — управління ролями;
– GET /profile, /profile/events, /profile/stats, /profile/attendance, /profile/team — особисті дані гравця.

Для управління сесією використовується React Context API (AuthContext). Контекст зберігає обʼєкт поточного користувача, надає функції login() та logout(), а також булеві прапори isAdmin та isCoach для рольового відображення елементів інтерфейсу.

Сторінка авторизації (LoginPage) дозволяє користувачеві увійти до системи. Після успішного входу backend повертає JWT-токен та обʼєкт користувача. Web-застосунок визначає роль користувача та перенаправляє його до відповідного кабінету.

У всіх сторінках зі списками реалізовано пошук та фільтрацію на стороні клієнта через useMemo(). Це забезпечує миттєву реакцію без додаткових запитів до сервера. Сортування таблиць виконується за клацанням на заголовок стовпця.

CRUD-операції відкривають модальне вікно (компонент Modal.jsx) із формою. Після успішного збереження або видалення виконується повторний запит до API та оновлення локального стану. Підтвердження видалення запитується через стандартний confirm().

2.7 Локалізація web-застосунку

Основною мовою web-застосунку є українська. Усі підписи, повідомлення, назви розділів, статуси та кнопки відображаються українською мовою. Дати та час форматуються через стандартний Intl API з локаллю uk-UA.

Повне перемикання між мовами в поточній версії не реалізовано. Однак структура застосунку дозволяє в майбутньому підключити інтернаціоналізацію через окремі файли перекладів.

3.1 UML-діаграма прецедентів

UML-діаграма прецедентів відображає основні ролі web-застосунку та функції, які вони виконують. У web-частині системи основними акторами є Адміністратор, Тренер та Гравець.

Адміністратор може виконувати всі дії тренера, а також управляти правами доступу користувачів. Тренер може переглядати та редагувати всі розділи клубу: команди, гравців, події, відвідуваність, статистику, медпункт та інвентар. Гравець взаємодіє лише зі своїм особистим кабінетом.

3.2 UML-діаграма компонентів

UML-діаграма компонентів описує структуру web-застосунку та його взаємодію з іншими частинами системи. Web-клієнт взаємодіє з backend-сервером виключно через REST API. Backend звертається до PostgreSQL для отримання та збереження даних.

Web-застосунок містить такі основні компоненти: LoginPage, Layout (з Sidebar та Outlet), набір сторінок для персоналу (Dashboard, Teams, Players, Events, Attendance, Stats, Injuries, Inventory, AdminUsers) та набір сторінок гравця (PlayerDashboard, PlayerEvents, PlayerTeam, PlayerMedical, PlayerStats, PlayerAttendance, PlayerProfile). Окремо виділено API-клієнт (utils/api.js) та AuthContext для управління сесією.

3.3 UML-діаграма пакетів

UML-діаграма пакетів відображає логічну структуру web-частини системи. У web-застосунку можна виділити такі пакети: pages (сторінки персоналу), pages/player (сторінки гравця), components (Sidebar, Modal, ProtectedRoute), context (AuthContext), utils (api.js) та стилі (App.css).

Пакет pages містить React-компоненти, що відповідають за основні розділи системи. Пакет utils забезпечує взаємодію з backend. Пакет context відповідає за управління станом авторизації. Такий поділ робить структуру застосунку зрозумілою та спрощує його подальший розвиток.

3.4 UML-діаграма взаємодії

UML-діаграма взаємодії описує сценарій відмітки відвідуваності тренером у web-застосунку. Процес починається з відкриття сторінки «Відвідуваність» та вибору події. Застосунок надсилає запит GET /attendance до backend, який повертає список гравців та їхні поточні статуси.

Тренер натискає кнопку статусу для кожного гравця. Web-застосунок надсилає POST /attendance з даними (event_id, player_id, status) до backend. Backend зберігає запис у базі даних та повертає підтвердження. Після успішної відповіді UI оновлює відображення статусу без повного перезавантаження сторінки.

5 ВИСНОВКИ

У ході лабораторної роботи було розроблено web-частину системи управління спортивними командами SportManager — повнофункціональний React-застосунок з рольовим доступом для адміністратора, тренера та гравця.

У процесі виконання роботи було виконано такі завдання:
– розроблено єдиний SPA-застосунок на базі React 19 + Vite з рольовою маршрутизацією через React Router DOM;
– реалізовано повний набір CRUD-операцій для команд, гравців, подій, відвідуваності, статистики, медпункту та інвентаря;
– розроблено особистий кабінет гравця з персоналізованим відображенням власних даних;
– реалізовано захист маршрутів через компонент ProtectedRoute та управління сесією через AuthContext;
– забезпечено адаптивну верстку — на мобільних пристроях сайдбар скривається та виїжджає через гамбургер-меню;
– розроблено UML-діаграми прецедентів, компонентів, пакетів та взаємодії;
– проведено функціональне тестування 12 сценаріїв — всі виконані успішно.

Розроблений web-застосунок успішно взаємодіє з REST API сервера SportManager та забезпечує зручний і функціональний інтерфейс для управління спортивним клубом.

utils/api.js — HTTP-клієнт з автентифікацією:
const BASE = '/api';

async function request(endpoint, options = {}) {
    const token = localStorage.getItem('token');
    const res = await fetch(`${BASE}${endpoint}`, {
        ...options,
        headers: {
            'Content-Type': 'application/json',
            ...(token &amp;&amp; { Authorization: `Bearer ${token}` }),
            ...options.headers,
        },
    });
    if (res.status === 401) {
        localStorage.removeItem('token');
        localStorage.removeItem('user');
        window.location.href = '/login';
        return res;
    }
    return res;
}

export const api = {
    get:    (url)       =&gt; request(url),
    post:   (url, data) =&gt; request(url, { method: "POST",   body: JSON.stringify(data) }),
    put:    (url, data) =&gt; request(url, { method: "PUT",    body: JSON.stringify(data) }),
    delete: (url)       =&gt; request(url, { method: "DELETE" }),
};

context/AuthContext.jsx — управління сесією:
import { createContext, useContext, useState } from 'react';

const AuthContext = createContext(null);

export function AuthProvider({ children }) {
    const [user, setUser] = useState(() =&gt; {
        try { return JSON.parse(localStorage.getItem('user')); } catch { return null; }
    });

    const login = (userData, token) =&gt; {
        localStorage.setItem('token', token);
        localStorage.setItem('user', JSON.stringify(userData));
        setUser(userData);
    };

    const logout = () =&gt; {
        localStorage.removeItem('token');
        localStorage.removeItem('user');
        setUser(null);
    };

    return &lt;AuthContext.Provider value={{ user, login, logout,
        isCoach: user?.role === 'coach' || user?.role === 'admin',
        isAdmin: user?.role === 'admin' }}&gt;{children}&lt;/AuthContext.Provider&gt;;
}

export const useAuth = () =&gt; useContext(AuthContext);

import { useState, useEffect, useMemo } from 'react';
import { api } from '../utils/api';

export default function EventsPage() {
    const [events, setEvents] = useState([]);
    const [search, setSearch] = useState('');
    const [timeFilter, setTimeFilter] = useState('all');

    useEffect(() =&gt; {
        api.get('/events').then(r =&gt; r.json()).then(setEvents);
    }, []);

    const filtered = useMemo(() =&gt; {
        let r = [...events];
        if (search) r = r.filter(e =&gt;
            `${e.title} ${e.location}`.toLowerCase().includes(search.toLowerCase()));
        if (timeFilter === 'upcoming') r = r.filter(e =&gt; new Date(e.event_date) &gt;= new Date());
        if (timeFilter === 'past')     r = r.filter(e =&gt; new Date(e.event_date) &lt;  new Date());
        return r.sort((a,b) =&gt; new Date(a.event_date) - new Date(b.event_date));
    }, [events, search, timeFilter]);

    // ... render table with filtered data
}
